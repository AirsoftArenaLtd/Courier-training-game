# C-40 accepted heavy-load policy core

Claude confirmed the posted solo limit as 50 lb (23 kg), with a critical only once an unassisted load above that limit actually leaves the floor. The new owned `fppackageheavy.js` core reuses the actual lifting bay and its bounded physical controls. It is deliberately not loaded or registered yet; owned UI/native/resource acceptance follows. No rendered or current-pilot result is claimed by these CPU checks.

The new two-load practice copies the existing 95 lb crate and awkward 35 lb box without changing the original five-load content or legacy result. Actual floor height controls the over-limit critical; gripping alone does not. An awkward load below the posted limit needs a balanced handling method but does not acquire the over-limit critical. The physical helper must arrive before gripping; the hand truck must be taken, pushed to the pallet and explicitly unloaded. The local ScoreLog checks knees, close grip, foot pivot, controlled placement and assistance/equipment; equipment uses actual handle/travel/unload observations instead of claiming manual posture. Completed safe methods share the 1,000-point scale. Repeated observations cannot dilute a critical or add checks. An unfinished run gives zero completion score/ratios with earned observations retained. No workday reports, saved fields or shared scoring implementation are added.

All **10 new physical core cases and 43 related cases** pass (eight suites). Tests include the exact 50 lb boundary, an initially safe grip followed by actual upward movement, correct and unsafe handling, helper arrival, equipment interlocks, zero on incomplete, and critical retention after a later good load. The first score comparison caught the shared ScoreLog's conversion of one check unit to 100 display points; the core now uses one-unit checks. That initial failed log is retained separately. `component-checks.json`, raw logs and `sources.json` retain the actual scope.

The three authorized existing m2 registry keys are applied for labels, sorting and lifting. Removing those keys reproduces the original registry byte for byte, preserving content, categories, ids, 2D scenes and defaults. The separate optional registry/launcher compatibility dependency remains with A-30, already raised in Claude's inbox for C-39. No new policy question is needed. New feedback sentences await Claude's translations once the UI is ready.
